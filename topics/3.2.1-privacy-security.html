Data Privacy Concerns vs Security Risks

Tell the two apart with confidence: privacy is about the data; security is about the system being attacked.

🧭 The one-line rule

Data privacy = is the data kept under control, not exposed, and handled lawfully?  Security = is the system / infrastructure protected from attack, breach, and unauthorised access? When in doubt, ask: "Is the problem about the data itself, or about someone attacking the system?"

🔐 Data privacy concerns about the DATA

Privacy concerns are about what happens to the data you put into (or get out of) a GenAI tool. The syllabus groups them into three:

1

Lack of control over data

You can't fully control how a GenAI tool (often a third-party/cloud service) stores, processes, or reuses the data you submit — it might even be used to train the vendor's models.

Example: You paste real customer records into a public chatbot whose terms say submitted content may be reused. You've lost control of that data.
🎯 Cue: "stored/processed/reused without consent", "vendor may train on your data", "don't know where data goes" → lack of control.
2

Unintentional data exposure

The model's output accidentally reveals sensitive information — e.g., confidential data that was in the prompt context, or another user's data — to someone who shouldn't see it. No attacker is involved; it's accidental.

Example: A generated test report unexpectedly prints API keys that were sitting in the prompt context, or surfaces another client's data.
🎯 Cue: "output accidentally reveals/leaks sensitive data", "no attacker" → unintentional exposure.
3

Compliance / regulatory

Using GenAI in a way that breaches data-protection regulations (e.g., GDPR) — including where data is stored/processed — risking legal disputes and penalties.

Example: Sending EU residents' personal data to a tool hosted in a non-approved region, risking a GDPR violation.
🎯 Cue: "GDPR", "regulation", "legal/compliance", "data residency" → compliance.

🛡️ Security risks about the SYSTEM

Security risks are about the LLM-powered test infrastructure being attacked — vulnerable to breaches, unauthorised access, and manipulative attacks. The defining feature is an attack on / compromise of the system (often deliberate).

Examples: the GenAI test platform's server is hacked; an intruder gains unauthorised admin access; a weak login lets outsiders in.
🎯 Cue: "breach", "hacked", "unauthorised access", "attacker compromises the system" → security risk.
Note: the specific attack vectors (data exfiltration, request manipulation, data poisoning, malicious code generation) are detailed in LO 3.2.2. For 3.2.1 you just need the high-level split: privacy (data) vs security (system).
⚠️ The classic trap — accidental vs deliberate: If sensitive data shows up in the output by accident (no attacker) → that's a privacy concern (unintentional exposure). If an attacker deliberately extracts or steals it by attacking the system → that's a security risk. Same data leaking, different category, decided by whether there's an attack.
