Metrics for Evaluating GenAI Results on Test Tasks

🧪 Our running example

You are testing the Login feature of a web app (the kind you automate with Selenium). You ask an LLM to generate test cases and automated test scripts from the requirements. Requirements include: valid login, wrong password, empty fields, account locks after 5 failed attempts, "remember me", and password rules (8–20 chars, at least one digit). We'll measure the AI's output with each metric below.

1

Accuracy

What it means

The overall correctness of the generated output compared to a trusted reference: expert-written test cases, the requirements, or a standard. "Did it get things right overall?"

Syllabus example: the degree to which the generated test cases cover all specified requirements.
On your work: The Login spec has 6 requirements. The AI produced cases that correctly cover 5 of them (it missed "account locks after 5 attempts"). → Accuracy ≈ 5/6 = 83%.
🎯 Exam cue: "overall correctness against requirements / expert cases / a standard" → Accuracy.
2

Precision

What it means

Correctness of the output with respect to one specific objective. Of what it produced for that goal, how much is actually correct/relevant? "When it flags something, is it right?"

Precision = correct items / all items it produced
Syllabus example: the degree to which the generated test cases correctly identify anomalies.
On your work: You asked it to generate cases that catch security anomalies on Login. It produced 10 such cases; 7 truly target real anomalies (SQL injection, brute-force, etc.), 3 are noise. → Precision = 7/10 = 70%.
🎯 Exam cue: "correctness for a specific objective", "correctly identifies anomalies", "few false positives" → Precision.
3

Recall

What it means

The ability to find ALL the relevant items that should exist. "Did it miss anything important?" (Completeness of coverage.)

Recall = relevant items found / all relevant items that exist
Syllabus example: the degree to which generated test cases cover valid and invalid equivalence partitions of a data class.
On your work: The password field has 8 equivalence partitions (valid length, too short, too long, no digit, only digits, special chars, empty, SQL-injection string). The AI covered 6 of 8. → Recall = 6/8 = 75%.
🎯 Exam cue: "covers ALL", "valid and invalid partitions", "completeness", "nothing missed" → Recall.
💡 Precision vs Recall (the classic confusion): Precision = "of what it produced, how much is correct?" (quality / few false alarms). Recall = "of everything it should have found, how much did it find?" (completeness / nothing missed).
4

Relevance & Contextual Fit

What it means

Whether the output is applicable and appropriate for your specific context — your test basis, your domain, your business rules — not generic boilerplate.

Syllabus example: the degree to which generated test cases are consistent with the test basis and integrate the domain-specific requirements.
On your work: Good fit = cases use your actual rules (locks after 5 attempts, password 8–20 chars) and your field names. Poor fit = generic "enter username/password" cases that ignore your business rules.
🎯 Exam cue: "consistent with the test basis", "domain-specific", "appropriate for the context" → Relevance & Contextual Fit.
5

Diversity

What it means

A wide range of inputs and scenarios is covered, avoiding repetition, and exploring edge cases — not 10 near-identical happy-path variations.

Syllabus example: the degree to which generated test cases cover various user behaviors and explore edge cases.
On your work: High diversity = it covers desktop + mobile, different locales, pasting the password, autofill, Caps-Lock on, very long input, network timeout mid-login. Low diversity = 8 cases that are all "valid login with slightly different valid passwords".
🎯 Exam cue: "variety", "avoids repetition", "various behaviors", "edge cases breadth" → Diversity.
6

Execution Success Rate

What it means

The proportion of generated test cases/scripts that actually run successfully — no syntax errors, no output-format problems — in an otherwise working environment.

Execution Success Rate = scripts that run / total scripts generated
Syllabus example: how many generated test scripts can be executed without syntax errors or output-format issues.
On your work: The AI generated 20 Selenium scripts for Login. 17 run without errors; 3 fail (bad locator syntax / wrong import). → Execution Success Rate = 17/20 = 85%.
🎯 Exam cue: "scripts that run/execute", "without syntax errors", "executable" → Execution Success Rate.
7

Time Efficiency

What it means

The time saved by using GenAI compared to doing the same work manually.

Syllabus example: time the AI needs to generate test cases vs the time a human would take to create equivalent tests.
On your work: The AI drafted 20 Login scripts in ~3 minutes; writing them by hand would take you ~3 hours. The time saved is the Time Efficiency gain.
🎯 Exam cue: "time saved vs manual", "faster than doing it by hand" → Time Efficiency.

⚡ Quick reference — pick the metric

If the question is about…The metric is
Overall correctness vs requirements / expert cases / a standardAccuracy
Correctness for one specific objective (e.g., correctly identifying anomalies)Precision
Covering ALL relevant items (valid + invalid partitions, completeness)Recall
Fitting your test basis / domain / business rulesRelevance & Contextual Fit
Variety, avoiding repetition, edge-case breadthDiversity
Generated scripts run without syntax/format errorsExecution Success Rate
Time saved vs manual effortTime Efficiency

🔍 How to apply these metrics (syllabus notes)

  • How to measure: by manual review, or automated by comparing the LLM output against a predefined reference.
  • Non-determinism: because GenAI output varies between runs, base your metrics on statistically relevant data (don't judge from a single run).
  • Task-specific metrics: beyond these general metrics, you can define metrics tailored to a specific test activity.
