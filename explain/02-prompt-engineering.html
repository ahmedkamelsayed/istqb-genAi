Prompt Engineering for Effective Software Testing

≈365 minutes · holds 5 of the 6 two-point K3 questions — the most important chapter

2.1.1 (K2) The six-component prompt structure

Memorize all six and be able to classify a given line into the right one (the exam tests this directly):

ComponentWhat it isExample phrase
RolePersona/perspective the model should adopt.“Act as a test automation engineer.”
ContextBackground about the test object / functionality.“You are testing a password-reset feature.”
InstructionThe directive — what task to perform (clear, imperative).“Generate test conditions from the requirements.”
Input dataMaterial to process: user stories, criteria, screenshots, code, logs, existing cases.“Use the attached raw test results / these reports & logs.”
ConstraintsRestrictions / special considerations on how to apply instructions.“Use Given-When-Then; exclude out-of-scope features.”
Output formatExpected structure/format of the response.“Provide a markdown table with columns ID, type, severity.”
Exam trick: a line listing data sources = Input data. A line saying how to present results = Output format. A line restricting the work = Constraints. The persona = Role.

2.1.2 (K2) Three core prompting techniques

TechniqueWhat it doesBest for
Prompt chainingBreak a task into intermediate steps (multiple prompts); check/refine each before the next.Complex tasks needing precision + human verification per step.
Few-shot promptingProvide examples. (zero-shot = none; one-shot = 1; few-shot = several.)Repetitive / fixed-format output (Gherkin, keyword-driven, fixed reports).
Meta promptingThe LLM generates/refines its own prompt; tester evaluates — a form of pairing with the AI.Flexible/dynamic tasks; crafting prompts for new tasks; when unsure how to word it.
🔑 Techniques combine: meta-prompt to draft → add examples (few-shot) → split into checked steps (chaining).

2.1.3 (K2) System prompt vs. user prompt

System promptUser prompt
Set byDeveloper/testerThe chatbot user
VisibilityUsually hidden / not editableVisible, the immediate input
LifetimeConstant for the session; sets rules/behaviorChanges each interaction
May containRole, context, constraints, general instructionsExplicit instructions + context + output format

The LLM answers by considering both together.

2.2 Applying techniques to test tasks (K3 — the 2-pointers)

2.2.1 (K3) Test analysis

GenAI can: identify defects in the test basis · generate test conditions from requirements/user stories · prioritize by risk (likelihood × impact, regulatory, user-facing, history) · coverage analysis (map requirements↔conditions) · suggest techniques (BVA, EP).

Typical chaining order on un-reviewed requirements: detect ambiguities → derive conditions → prioritize by risk → coverage. On already-reviewed/stable requirements: skip defect detection.

2.2.2 (K3) Test design & implementation

Test case generation (preconditions, inputs, expected results, coverage) · synthetic, privacy-preserving test data · automated script generation · execution scheduling/prioritization.

Pattern: structured prompt to generate → coverage table verifying each acceptance criterion → meta-prompt to build end-to-end procedures. Use few-shot for Gherkin (Given-When-Then) cases.

2.2.3 (K3) Automated regression testing

Grows each release → ideal for automation in CI/CD. GenAI helps with:

  • Keyword-driven script implementation (map keywords → steps).
  • Impact analysis → target high-risk areas.
  • Self-healing / adaptive tests → auto-adjust to minor UI/API changes (e.g., dynamic locators) → fewer false failures.
  • Automated reporting & insights, defect reporting + root-cause (logs, screenshots, env data).

GUI tests break on UI change; API tests on changed request/response/endpoints/auth → GenAI adapts scripts & data. Always review output by risk.

2.2.4 (K3) Test monitoring & control

  • Monitoring = analyze trends, predict risk, alert on deviations; metrics visualization/reporting, NL summaries, dashboards, completion reports.
  • Control = act on the data: reprioritize tests, adjust schedules, reallocate resources to high-priority areas.
Exam distinction: dashboards/summaries = monitoring/reporting; reprioritizing & reallocating = control.

2.2.5 (K3) Choosing the technique — the decision table

Task characteristicTechnique
Complex, needs precision + per-step human checkPrompt chaining
Repetitive / specific constrained output formatFew-shot prompting
Flexible/dynamic, or crafting a prompt for a new taskMeta prompting
No examples, just rely on model knowledgeZero-shot

2.3 Evaluate results & refine prompts

2.3.1 (K2) Metrics for GenAI results on test tasks

MetricMeasures
AccuracyOverall correctness vs expert cases/requirements/standards.
PrecisionCorrectness w.r.t. a specific objective (e.g., correctly identifying anomalies).
RecallAbility to find all relevant instances (e.g., covering valid and invalid equivalence partitions).
Relevance & contextual fitOutput is applicable/appropriate for context & domain.
DiversityWide range of inputs/scenarios, edge cases; avoids repetition.
Execution success rate% of generated cases/scripts that run without syntax/format errors.
Time efficiencyTime saved vs manual effort.
Because GenAI is non-deterministic, base metrics on statistically relevant data. Pair metrics to the goal (e.g., diversity for edge cases + execution success rate for API scripts).

2.3.2 (K2) Techniques to evaluate & refine prompts

  • Iterative prompt modification — start with a base prompt, refine gradually.
  • A/B testing of prompts — compare versions against predefined metrics.
  • Output analysis — examine output for inaccuracies → diagnose why it went wrong (best for “why are results wrong?”).
  • Integrate user feedback — testers’ input on usefulness/clarity.
  • Adjust prompt length & specificity — more context helps sometimes; shorter helps generalization other times.
🔑 Share prompt libraries across the team to standardize quality.
